# Functional requirements traceability

**Source:** finalized Functional Requirements: Event Dynamics, 263 requirements, supplied 19 September 2026.
**Contract:** Event Dynamics API v0.2.0 and its AsyncAPI companion.
**Result:** 263/263 requirements have a contract mapping. “Contracted” means the API describes the surface and required behavior; it does not mean a backend, authorization matrix, provider integration, or performance test has passed.

The operation names below are the stable `operationId` values in `event-dynamics-openapi.yaml`. Requirements that describe local device behavior, manual UI parity, scheduled retention, or system invariants are mapped to the API command/read model and remain implementation acceptance work.

## Interpretation and remaining evidence

The matrix closes the previously missing requirements-register review. It does not replace implementation evidence. The implementation must still prove current authorization, transaction boundaries, idempotency, concurrency, retention jobs, device cryptography, provider reconciliation, browser behavior, and NFR targets using the acceptance scenarios.

The three most implementation-sensitive mappings are:

- FR 181–185: offline admission has a REST preparation/sync contract, but the local device verifier and offline client must be tested separately.
- FR 214: every AI-supported normal operation must remain available through standard manual UI/API actions; the API cannot prove UI parity by itself.
- FR 257: the AI ledger includes failure-credit entries; the worker must append a compensating credit only for an internal platform failure, never for user cancellation or provider failure.
